# ADR-006：采集存储阈值与最旧数据清理

日期：2026-10-30。状态：已采用。

采集资料持续增加，实例需要容量上限及自动淘汰策略。默认设置 DATABASE_MAX_SIZE_GB=5（十进制 GB），达到阈值时自动淘汰最旧采集数据，目标为上限的 90%，可通过 DATABASE_CLEANUP_TARGET_RATIO 调整。本决策替代 ADR-001 中历史无限保留的约定。

容量口径为所有应用表的有效数据估算：变长字段按数据库实际字节长度汇总，加上固定字段、行及索引的估算开销；包含个人资料、配置和创作脚本。这不是数据库文件、日志、备份、临时文件或服务器磁盘的硬配额。MySQL 已分配空间不会在 DELETE 后立即缩小，且 information_schema 统计有延迟，不能据此循环删除直到文件变小。清理释放的空间可供后续数据复用，不自动执行 OPTIMIZE TABLE。需要严格磁盘容量限制时由部署环境设置配额。

GitHub 与知识采集在网络请求前检查，提交新增数据前再次预留整批空间。两类 worker 通过同一 MySQL 连接级存储锁串行执行检查、清理和入库，避免同时判断有空间后重复占用。删除按照 GitHub 批次 started_at 与知识选题 collected_at 比较，以最旧采集时间为先；单次最多淘汰 1000 个批次/选题，减少无限清理的风险。若目标未达到但当前批次仍有空间则继续采集；空间仍不足时停止本轮，由下一轮继续检查。单批预留已经超过上限时先拒绝，不因此删除历史。

保留所有个人记录引用的知识选题（包括取消收藏但仍有备注的记录）、创作卡片引用的选题、最新写入的一个知识选题。GitHub 保留每个仓库最新快照所在的完整批次、最近两个成功批次、最近 26 小时批次及运行中批次，保证项目详情、近期榜单对比及 24h 增长基线。批次淘汰时先删除 rankings，再删除 snapshots，最后删除 collection_runs，历史详情不会变成部分缺失的榜单。知识选题先删渠道引用再删原记录。仓库身份、来源配置和用户资料不删除。

用户写备注或创建卡片时先锁定原选题；清理锁定候选选题后使用当前读重新确认引用，避免与用户写入产生悬空记录。删除分次提交；若后续采集失败，已清理的历史不会恢复。自动清理是永久删除，备份由部署方维护。

采集状态 API 增加 storage 字段（used_bytes、limit_bytes、cleanup_target_bytes、usage_percent、over_limit、measurement），前端显示估算口径、容量和保留规则。每次清理记录前后容量、删除批次/快照/选题数量；空间不足记录明确错误。验证使用启用外键的隔离 SQLite 数据库；真实 MySQL 验证仅允许专用测试库，不对业务库执行测试删除。
